# 正式与本地打板回测一致性审计

## 结论

- 正式环境运行 `v2.5.18`，镜像 revision 为
  `e4684658238ca003b95c7f5319b4ba3f52781a56`，对应
  `limit-up-history-v14 / limit-up-live-v4 / limit-up-scheduled-v3`。
- 正式回测只有 13 个信号、2 笔闭合交易，胜率 50%，账户收益
  `-0.6152%`。正式 `/data-quality` 同时明确返回
  `research_ledger_ready=false` 和 `simulation_eligible=false`。
- 本地用同一个 `v2.5.18` 镜像、同一个 `2025-06-10..2026-07-15`
  选择区间读取本地完整证据，仍得到 290 个信号、139 笔闭合交易、
  胜率 `62.5899%`、收益 `+224.0076%`、最大回撤 `-7.9408%`。
  因此 603 日与 268 日的显示范围不是本次巨大差异的直接主因。
- 直接主因是正式库只有 18 个涨停事件交易日、1,870 条可用事件，
  本地有 258 个事件交易日、20,910 条事件。正式环境没有执行同花顺
  近 252 日一次性历史证据回补，夜间调度也不包含这项回补。
- 本地当前工作区还有未发布的 v15/v6/v4 改动。完整本地库下，v15
  综合首板与二进三为 307 个信号、149 笔交易、收益 `+266.4491%`。
  这部分相对已发布 v14 增加 `42.4415` 个百分点，但不能解释正式环境
  从 `+224.0076%` 变成 `-0.6152%` 的主体差异。

## 根因链路

1. `sync_stock_daily_bars` 的正式任务默认参数仍是 `limit=250`。数据健康
   只检查是否更新到最新交易日，不检查纵向回测深度，所以页面显示日线
   “新鲜”，但历史账本仅完成目标 500 日的 `53.6%`。
2. 正式调度只有实时涨停池和 `sync_limit_up_event_minutes`。后者只能给已存在
   的事件补分钟线，不能创造缺失的 252 日历史事件。
3. `sync_limit_up_ths_evidence` 只由数据页后台批次触发，不在 `eod_1900` 或
   `eod_finalize_2130` 中。正式库因此只保留近期东方财富事件，事件门禁仅
   `18/500 = 3.6%`。
4. `/limit-up` 回测页仍展示部分账本计算出的账户指标，只以“研究账户”弱提示，
   没有在 `research_ledger_ready=false` 时隐藏或阻断主指标，放大了误解。
5. 正式服务器和容器均健康；审计时 API 约占 706 MiB 内存、CPU 约 2%，
   PostgreSQL 约占 230 MiB，未发现回测接口错误。8 核 16 GiB 不是本次根因。

## 修复顺序

1. 先备份正式 PostgreSQL 数据目录或数据库。
2. 在正式环境完成同花顺近 252 日事件回补，再重建 v14 历史账本；先验证
   事件覆盖、信号数和 v14 指标是否与“正式镜像 + 本地库”对照收敛。
3. 另行补齐至少 600 个交易日的全市场日线和财报覆盖。日线任务必须使用
   非增量历史回补参数，普通夜间增量任务不会向更早日期回填。
4. 当前本地 v15/v6/v4 改动完成测试、提交、打 tag 和镜像发布后，才能比较
   `+266.4491%` 口径；不能要求 v2.5.18 自动得到未发布策略结果。
5. 增加部署验收门：镜像 revision、历史版本、可靠日线数、事件交易日、
   财报覆盖、信号数和 `research_ledger_ready` 必须同时通过；部分账本应在
   产品页 fail closed，不能把 2 笔交易作为正式回测主结果。

## 验证边界

- 审计全程只读，没有修改正式代码、配置、调度、数据库或容器状态。
- 历史结果仍大量使用收盘价代理，且 Tick/L2、竞价、逐日概念成员和 60 日
  真实前向证据未齐，`simulation_eligible` 继续为 `false`。
